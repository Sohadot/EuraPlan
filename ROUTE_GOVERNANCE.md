## 1. Route Architecture Doctrine

EuraPlan.com uses a three-layer governed route architecture.

**Layer 1 — Heavy Reference Ontology Pages**
Deep, structured, source-backed pages on regulation, countries, sectors, and funding.
These are the SEO and authority foundation of the category claim.
They are permanent, non-combinatorial, and individually justified.

**Layer 2 — Canonical Diagnostic Engine**
One canonical path: `/diagnostic`
The entry point for interactive planning intelligence.
Context (origin, entity type, sector, country, objective) is carried by the diagnostic system — not multiplied into URL parameters indexed by search engines.
Diagnostic query states are never indexed and never appear in sitemap.xml.

**Layer 3 — Pre-Composed Briefs**
Under `/brief/...` only.
Published only when justified by confirmed real demand or a specific named strategic opportunity.
Never created speculatively.

---

## 2. Combinatorial URL Prohibition

**Permanently prohibited:**
- `/enter/us/saas/germany/`
- `/clock/ai-act/us/saas/`
- `/brief/gdpr/uk/fintech/phase-2/`
- Any URL generated by combining ontology dimensions (origin × entity type × sector × country)

Context is carried by the diagnostic and planning system. It is not mapped into the URL tree.

**Rationale:** Combinatorial URL expansion destroys crawl budget, produces structurally thin pages, and dilutes the category authority signal. It also creates maintenance obligations that cannot be honoured at scale.

## 3. Route Approval Requirements

A route may only be created when all of the following are confirmed:

- route_id assigned
- Purpose documented (not "TBD")
- Ontology class or doctrine role defined
- Page thesis written (one clear sentence)
- Target audience identified
- Decision problem identified
- Intelligence output or doctrine purpose identified
- Source requirement assessed
- Indexable status confirmed
- Minimum two internal links confirmed (to and from existing routes)

Routes that do not meet these requirements remain at `status: draft` and are not published.

---

## 4. Indexing Rules

| Route Type | Indexable | Sitemap |
|---|---|---|
| Reference ontology page | Yes | Yes |
| Diagnostic engine (`/diagnostic`) | Yes — entry point only | Yes |
| Diagnostic query state (`/diagnostic?...`) | No | No |
| Brief (`/brief/...`) | Yes | Yes (when published) |
| Governance and source pages | Yes | Yes |
| Draft routes | No | No |
| Internal tooling or admin paths | No | No |

Diagnostic query states must never appear in sitemap.xml.
Diagnostic query states must be disallowed in robots.txt.

---

## 5. Route Lifecycle

1. **Proposed** — Route identified, purpose drafted, not yet approved
2. **Approved** — All route approval requirements met, ready for development
3. **In Development** — Page content being built
4. **Published** — Live and indexable
5. **Under Review** — Content under update, may remain live with review notice
6. **Deprecated** — Removed from sitemap, disallowed in robots.txt, redirected

---

## 6. Redirect Policy

Deprecated routes that received public traffic must redirect (301) to the most relevant live route.
Never return a 404 for a previously indexed route without a redirect in place.

---

## 7. Route Registry

All approved routes are maintained in `routes.json`.
No route is considered governed without an entry in `routes.json`.
`routes.json` is the single source of truth for route state.
